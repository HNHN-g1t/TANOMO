# 詰める

実装前に、判断を1つずつ確定させる。

**詰め切る前に実装しない。やり直しが激減する。**

丸投げで作ったものは、たいてい一般論になり、作り直しになる。先に1往復する方が結果的に速い。

## 進め方

**質問は1回に1つ。** まとめて5問投げない。1問ずつ答えてもらい、その答えで次の枝が決まる。並べて出すと、答えが浅くなり依存関係も見えなくなる。

**推奨回答を必ず添える。** 「どうしますか？」で終わらせない。「AとBがあります。**Aを推します**（理由）」まで書く。ユーザーは「それで」と言うだけで前に進める。判断を丸投げしない。

**調べて分かることは聞かない。** コードベース・既存ファイル・git履歴を見れば答えが出るものは、自分で見る。「どのフレームワークですか？」は質問ではなく怠慢。

**依存の上流から聞く。** 答えで下流の質問が消えるものを先に。「誰が使うか」が決まれば「どの端末で見るか」は自動で決まることがある。

## 判断の型

### 聞く順番は「目的 → 制約 → 形 → 細部」

1. **目的** — 何がどうなれば成功か。誰が使うか
2. **制約** — 期限・予算・既存資産・触ってはいけないもの
3. **形** — 画面か、CLIか、ファイル出力か。どこで動くか
4. **細部** — 色、文言、項目名

細部から聞くと、目的が変わった瞬間に全部やり直しになる。

### 「どちらでもいい」は確定として扱う

ユーザーが「任せる」と言ったら、そこで止まらない。**こちらが決めて、決めた内容を1行で明示して進む。**

「任せます」を「まだ決まっていない」と解釈して質問を重ねるのが、いちばん時間を溶かす。

### 外部サービスの手動設定は最初に全部出す

APIキーの取得、ドメイン設定、権限付与、課金登録 ——**本人にしかできない操作は、着手前にまとめて提示する。**

作り終わってから「あとはこれを設定してください」と出すと、そこで詰まって成果物が死ぬ。

### 金がかかるなら先に金額を言う

API・外部サービスを使う設計なら、**1回いくら・月いくらを着手前に出す。** 公開範囲によるリスクも同時に言う。

作ったあとで課金額を知らせるのは、選択肢を奪ったことになる。

### 止め時を決めておく

詰めるのは手段であって目的ではない。次のどれかで止める。

- 実装に必要な判断が全部埋まった
- 残りの分岐が「あとで直せる」ものだけになった
- 質問が細部（色・文言）に降りてきた

止めたら、**確定事項を箇条書きで並べて確認を取る。** そこから実装に入る。

### 決めたことは残す

詰めた結果は会話に埋もれる。確定事項は**その場で1箇所にまとめて出す**。

```
確定：
- 対象   ： 〇〇
- 出力   ： 〇〇
- 制約   ： 〇〇
- 未決   ： 〇〇（あとで直せる）
```

次のセッションに引き継ぐときも、これをそのまま渡せる形にしておく。

## やらないこと

- 質問を5つ並べて投げる
- 推奨なしで「どうしますか？」と返す
- 調べれば分かることを聞く
- 細部（色・文言）から聞き始める
- 確定事項を書き出さないまま実装に入る
- 「念のため」で質問を増やす（**答えで成果物が変わらない質問はしない**）

## 仕上げ

詰め終わったら、確定事項の一覧を出して確認を取る。
確認が取れたら実装へ。画面を作るなら `yasumushiki`、書きもの・企画なら `kashikoi-shigoto` に渡す。
