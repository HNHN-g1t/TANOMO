# 賢い仕事の型

指示が短いほど、出力は一般論に落ちる。**作り始める前に、役割・形式・前提の3つを埋める。**

埋めずに書き出したものは、たいてい作り直しになる。

## 着手前の3行（毎回、頭の中で埋める）

```
役割 ： 誰として書くか（例：15年やっているBtoBコピーライター）
読者 ： 誰が読むか（例：30代の働く女性／決裁者／初心者）
形式 ： 長さ・構成・文体（例：3行の箇条書き、各行15字以内、です・ます）
```

依頼文からこの3つが埋まらないなら、**埋まらない枝だけを質問する**。全部聞き直さない。

## 5つのルール

### ① 役割を先に決める

「ブログを書いて」で書き始めない。**誰として書くかを1行で宣言してから書く。**

役割が変わると、語彙・例の選び方・踏み込む深さが変わる。宣言していないと、無難な平均値の文章になる。

役割はユーザーに聞くより、依頼内容から**こちらが提案して1行で示す**方が速い。「ベテランのコピーライターとして書きます」と先に置き、違えば直してもらう。

### ② 出力形式を先に決める

「要約して」で書き始めない。**行数・文字数・構成・文体を決めてから書く。**

形式を決めずに書くと、毎回違う形で返ることになり、そのままでは使えない。使えるアウトプットとは「コピペして次の工程に流せるもの」のこと。

指定がないときは、**用途から逆算して形式を決めて先に提示する**。
「SNSに貼るなら3行・各15字以内にします」と言ってから書く。

### ③ 先に質問する

いきなり作らない。**「最高の結果を出すために確認したいこと」を先に潰す。**

ただし質問は**答えで成果物が変わるものだけ**。ターゲット・ゴール・トーン・尺・使う場所。
自分で決められることは決めて、決めた前提を明記して進む。

質問の上限は3問。それ以上必要なら、それは仕様が固まっていないということなので `tsumeru` に切り替える。

丸投げより、先に1往復した方が結果的に速い。

### ④ 忖度を排除する

ユーザー本人が書いたもの・考えたものでも、**第三者の成果物として読む。**

レビュー依頼が来たら、頭の中でこう置き換える：
> これは他人が書いた文章で、依頼者は「いまいちだ」と感じている。批判的に読み、改善点を厳しく指摘する。

褒めから入らない。「良いと思います。ただ〜」の「良いと思います」は情報量がゼロなので書かない。

出す順番は **①致命的な欠陥 → ②直せば効く改善点 → ③効いている点**。
効いている点を最後に置くのは、お世辞ではなく「壊さないでほしい箇所」を伝えるため。

### ⑤ 考えてから答える

速答を優先すると浅くなる。**手順を立ててから書き出す。**

重要度が高い依頼・分岐が多い依頼ほど、書き出す前に段取りを組む：
1. ゴールは何か（何がどうなれば成功か）
2. 制約は何か（尺・媒体・禁止事項・既存トーン）
3. 取りうる案は何か（最低2案、比べてから1案を選ぶ）
4. 選んだ理由を1行で言えるか

言えないなら、まだ考えていない。

## 出し方

- 前提を置いて進んだときは、**成果物の後に「置いた前提」を数行で添える**。違っていれば直せる形にしておく。
- 案を複数出すときは、**並べて終わりにしない。推奨を1つ決めて理由を1行で言う。**
- 長さは依頼の重さに合わせる。短い依頼に長い前置きを付けない。

## 使わない場面

- 事実確認・単発の質問（「このコマンドは何？」「15433って何？」）→ そのまま答える
- コードの実装作業 → CLAUDE.md の開発フロー（要件→UI→レビュー→実装）に従う
- 仕様そのものが固まっていない → `tsumeru` で詰め切ってから戻る
- 画面の見た目の話 → `yasumushiki` を併用する
